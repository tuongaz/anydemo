## Codebase Patterns
- Studio sources live in `apps/studio/src/` with co-located `*.test.ts` (Bun test). Run a single file with `bun test apps/studio/src/foo.test.ts` from repo root.
- Pub/sub modules follow the `createX(deps)` factory pattern (see `events.ts`): closure-captured state, `subscribe(fn)` returns an unsubscribe closure, throwing subscribers are caught + logged without affecting others.
- Quality gate order: `bun run format` (biome --write) → `bun run lint` (biome check) → `bun run typecheck` (fans out via concurrently).
- Typecheck needs `@seeflow/canvas` built first (`cd packages/canvas && bun run build`) because schema.ts imports `@seeflow/canvas/catalog` types from its dist.
- Biome strict on unused variables — use `// biome-ignore lint/correctness/noUnusedVariables: <reason>` when reserving a slot for an upcoming story.
- `noUncheckedIndexedAccess` is on — array access returns `T | undefined`; use optional chaining or guards.

- **Learnings for future iterations:**
  - When refactoring a state machine that uses Promise-local `let settled = false` for the boot-window-guard, the cleanest way to let an external method (stop) interrupt is a `BootHandle` object in closure scope. Putting `settled` on an object (instead of a `let`) gives external callers a way to flip it before the in-flight callbacks check it. Reusable pattern for any "start-then-cancel" async flow.
  - The order `handle.settled = true` → `transport.close()` is load-bearing during a starting→stop abort. Real and fake transports both can synchronously emit `closed` from inside `close()`; if the boot callback still sees `settled === false`, it will reject with the wrong reason AND run a duplicate state transition. Flip the flag first, then close.
  - For object-literal methods that need to call sibling methods (e.g. `rotateUrl` calling `stop()` and `start()`), assigning the literal to a `const controller: ShareController = {…}` and returning it lets sibling methods call `controller.stop()` without relying on `this`. Safer than method-shorthand `this` when the controller object is destructured or passed around.
  - In `makeFakeTransport`, expose `instanceCount()` + `closeCount()` (not just `wasClosed()`) when you want to assert lifecycle correctness across rotate/restart flows — `wasClosed` is sticky and tells you nothing about a second transport instance.
  - `mockFetchSequence([{body:…},{body:…}])` is the standard 'two-call' fetch double for rotate-style tests; reuse rather than redefine per-test. Drops back to the last response if called more than `responses.length` times to avoid undefined-deref under noisy reconnect logic.
  - The `await new Promise<void>((resolve) => { const off = ctrl.subscribe((s) => s.status === 'starting' && (off(), resolve())); })` pattern is the right way to await a specific state transition before kicking the next action — far more deterministic than `await Promise.resolve()` choreography.

  - The order `subscribeToEventBus()` BEFORE `setState({status:'active', ...})` is deliberate: if a state subscriber synchronously broadcasts an event in response to the transition (e.g. a UI hook firing `node:status idle`), we want the bridge already wired. Mirrors the same "open audit log before transition" rule from US-020.
  - `EventBus.broadcast` uses synchronous Set iteration; subscribers added or removed mid-iteration are NOT observed by that broadcast. That means if a subscriber side-effectfully calls `subscribeToEventBus()` again, the new subscriber won't fire on the same broadcast. Today this never happens (we only subscribe in start()), but document it before adding mid-session subscription rotation.
  - `let eventUnsubscribes: (() => void)[] = []` (not `const`) because `unsubscribeFromEventBus()` reassigns the array — capturing the old array locally, replacing with a fresh `[]`, then iterating. Avoids the "what if a subscriber unsubscribed itself" foot-gun by snapshotting before iterating.

  - The `controller.subscribe(fn)` contract from US-014 — "fn is called synchronously once with current state, then on every transition" — IS the SSE initial-frame mechanism. One subscribe == one initial + N transitions.

A single `reader.read()` will often return only the headers' initial flush; the actual event frame comes in a subsequent chunk. - **Learnings for future iterations:**
  - Bun.serve's `<T>(...) ` generic + `srv.upgrade(req, { data })` is the canonical pattern for per-connection state — `ws.data` is typed as `T` inside the websocket handlers (`open`/`message`/`close`). No per-conn Map<id, state> needed for the basic case; the data object IS the state. Keep a Map<connId, ServerWebSocket<T>> only when you need to send TO a specific peer from outside that peer's own handlers (like our routing fan-out).
  - The real relay's `ws-default.ts` `routeFrame` does NOT rewrite `env.from`; it forwards as-is. But the host's `share.ts` `handleFrame` uses `env.from` as the connId for `peerConnIds.set(peerId, env.from)`. In production, the peer canvas must set `from` to its own AWS API Gateway connectionId for kick routing to work end-to-end — currently the peer has no way to learn that ID (ws-connect.ts is a no-op). The FakeRelay papers over the gap by rewriting `from` to the server-assigned connId. Note for phase 3+: the peer canvas needs an on-connect "you are <connId>" frame, OR the relay needs to do the rewrite for real. Filed as a phase-2 gap, not a blocker.
  - For Bun-test integration tests, `Bun.sleep(25)` is a cheap deterministic-enough way to let loopback message dispatch settle between `peer.send(authPeer)` and `peer.send(presenceJoin)` — without it, the relay might not have registered the peer in `sessionPeers` before the second frame routes (and presence has no error visibility — silently fails). `waitUntil(cond, ms)` polling on observable state is the right tool when there IS observable state; `Bun.sleep` is the fallback for "wait one tick".
  - When the share controller is reused via `await fetch('/api/share/start')` after a stop, the studio creates a brand-new `BootHandle` + opens a fresh WS to the relay. The fake relay correctly assigns a new connId and tracks `hostConnectionCount` as a monotonic counter — distinguishing "ever connected" from "currently connected" (`hasHostFor(sessionId)`). Both observable types are useful: monotonic for "did the second start succeed", current for "did the first stop take effect".
  - `await sse.waitFor((e) => e.event === 'state' && ...)` is the right shape for our /api/share/state stream — the SSE handler uses `streamSSE` with `event: 'state'` frames, NOT default `message` events. Predicate must check `e.event === 'state'` or it'll match the heartbeat (`: ping`) lines, which `connectSse` doesn't surface as events but other implementations might.
  - The pre-existing integration suite has 5 flaky tests (subprocess spawn timeouts, ConnectionRefused) — pre-existing, NOT introduced by this story. New tests pass cleanly in isolation in ~500ms.
