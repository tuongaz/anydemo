- Phase 3 work happens in a sibling repo at `/Users/tuongaz/dev/seeflow-viewer` on branch `ralph/live-share-phase-3` — NOT in the seeflow monorepo. cd there before running bun/git commands.
- `seeflow-viewer` uses Bun + Vite + TypeScript strict. Tests live beside sources as `*.test.ts` and run via `bun test`.
- `tsconfig.json` has `noUncheckedIndexedAccess` enabled; add `"bun"` to compilerOptions.types to pick up `bun:test` types when adding @types/bun.
- Vite only entry-points `index.html`, so `*.test.ts` files are never bundled into `dist/` automatically — no need for explicit excludes.
- Match `@types/bun` version to the installed bun runtime (`bun --version`) to avoid type drift.
- The canonical envelope schema for the relay WebSocket lives at `cloud/lambda/share/shared/envelope.ts` (server-side). The peer-side mirror is `src/lib/share-envelope.ts` and MUST stay aligned — when the relay adds a new `type`, mirror it here. Phase 3 adds `flow-snapshot` and `auth-refresh-required` that are NOT yet in the cloud-side enum.
- The relay (`cloud/lambda/share/ws-default.ts`) does NOT emit an explicit auth-ack frame — it returns 200 over HTTP. Peer-side `ShareClient.connect()` uses a 250ms quiet-window after sending `auth-peer` to treat auth as acknowledged. Any inbound frame within that window also counts as ack. Do not wait on a frame that never arrives.
- For WebSocket-driven unit tests, inject a fake constructor via `webSocketImpl` (defaults to `globalThis.WebSocket`) — keeps tests offline and deterministic. Pattern lives in `src/lib/share-client.test.ts`.
- For `globalThis.fetch` mocks in bun:test, swap `globalThis.fetch` in `beforeEach`/restore in `afterEach`. Use `Response(JSON.stringify(...), { status })` to construct realistic responses without pulling in any test helper. Pattern lives in `src/lib/share-api.test.ts`.
- Share peer-side error contract: `ShareTokenError('unknown-token')` on HTTP 404, `ShareTokenError(body.error ?? 'bad-request')` on HTTP 400, plain `Error` with status code on other failures. The cloud-side handler at `cloud/lambda/share/session-join.ts` is the source of truth for the `body.error` strings (`missing-token`, `missing-displayName`, `unknown-token`, `invalid-json`).
- `ShareSession`'s WS lifecycle: a second `useEffect` keyed on the join response object (NOT on individual fields) instantiates `ShareClient`, subscribes via `on('state', ...)`, calls `.connect()` (catching to swallow rejections — the state listener is the source of truth for UI), and cleans up with `unsubscribe()` + `client.disconnect('unmount')`. A `retryNonce` state value bumps the join-effect's dep array so Retry re-runs `joinShare` cleanly without nuking the displayName.
