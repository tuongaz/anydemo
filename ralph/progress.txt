- **Drawable types:** Only the 9 GeometricNodeType tags are click-drawable. image/html/icon need upload / dedicated authoring flows.
- **useState declaration order is load-bearing** in `seeflow-canvas.tsx` (~12 useState slots). When adding state, ALWAYS append at the END of the component body — never insert at top. Hook-shim tests use `useStateOverrides[N]` indexed by declaration order. See `packages/canvas/CLAUDE.md`.

The other geometric shapes (database/queue/cloud/server/user/ellipse/sticky/text) are for purely visual annotations where chrome isn't wanted. Skill prompts, agent worked examples, and tech refs all converged on this default.

ResolvedFlowSchema (the merged-with-style read shape) is INTENTIONALLY non-strict — extra fields are silently dropped to allow forward-compat. When testing "image-only field rejected on rectangle"-style invariants, construct the malformed node directly + assert `FlowSchema.safeParse` fails — the route layer is a soft gate, the disk is the source of truth.

The `test-integration.ts` orchestrator has an mtime-based freshness check that auto-rebuilds; `run-e2e.ts` does NOT. The classic symptom of a stale SPA: e2e fails with `[data-node-type='rectangle']` matching 0 elements while React Flow successfully renders 6 group containers (the SPA falls back to React Flow's default node renderer when its nodeTypes map doesn't recognize the type). - **`buildNewShapeData` returns `data` WITHOUT a `shape` field** under the flat schema (US-010 hard-fix). The on-disk strict FlowGeometricNodeData schema rejects unknown keys, and `shape` is neither a known data flow key nor a known style key, so merge.ts keeps it on flow.json where the strict check catches it. Any helper that builds new-node data MUST stay within {NODE_DATA_FLOW_KEYS} ∪ {NODE_STYLE_KEYS} — those are the routing tables in `apps/studio/src/merge.ts`. The canvas adapter's `NodeCreateInput.data: Record<string, unknown>` is permissive and won't catch this at typecheck; the studio's strict schema does, surfacing as 'Couldn't save change: Flow failed schema validation' from the createNode route.
- **Ellipse + sticky render `data.description` as their primary label, NOT `data.name`.** Under the flat-schema renderer, `isDescriptionLabelShapeNode = node.type === 'ellipse' || node.type === 'sticky'`, so any fixture seeding a visible-text ellipse / sticky must set `data.description`. Setting only `name` renders empty text. The detail-panel + the e2e fixtures had to be updated to thread the right field.
- **For draw-mode shape buttons under the flat schema:** only `rectangle` + `ellipse` are top-level toolbar buttons (`toolbar-shape-rectangle` / `toolbar-shape-ellipse`). `sticky` + `text` are in a separate secondary cluster but still top-level (same testid pattern). Any e2e or test that arms an illustrative shape must click the picker first; checking via `toolbar-shape-database` will always 0-match.
- **Direct event dispatch via `locator.dispatchEvent(type, init)` bypasses Playwright's topmost-element resolver** and dispatches the event on the locator's resolved element. Use this for any e2e that needs to fire a pointer event on a specific DOM element regardless of what's stacked above it (popover backdrops, draw-ghost overlays, etc.). `page.mouse.*` targets coordinates and intermittently hits the wrong element under React Flow's pane-stacking model.

**Learnings for future iterations**

- **The "bun test passes" AC was much wider than US-009's per-test additions.** Pre-existing migration gaps from US-001..US-008 (13 test files + 2 source files) had to be fixed in US-009 because they shared the same "bun test" surface. Big lesson: when an early PRD-mandated AC says "tests pass" but the schema cutover is wide, EVERY consumer of the old schema must be migrated atomically (or in the same single uncommitted batch) — letting individual stories defer fixture cleanup creates a long tail of pre-existing failures the testing story has to absorb. For future similar refactors: add a US-002 or earlier "migrate every studio test file + fixture" story before any feature-test stories start.
- **Python-script bulk migration is the right tool for repetitive schema flips across N files.** The migration script (`/tmp/migrate_studio.py`) handled `type: 'shapeNode' + data: { shape: 'X' }` → `type: 'X' + data: {}` flips across 10 files in one pass, with a loop to drain multi-comma cases. Sed alone struggles with the structural rewrite (needs to lift `shape: 'X'` out of `data: { ... }` while preserving the other keys); a Python regex with capture groups handles it cleanly. Verify with `grep -c` afterward.
- **The parallel-walk pattern (orig vs current line-by-line) drifts when the current file added lines.** When restoring `playRectangle`/`stateRectangle` helpers from the original `playNode`/`stateNode`, the line-count drift caused the last 3 lines of the file to be truncated. Always check `wc -l` before/after a parallel-walk script and re-add the trailing content if drift is detected. (Or: use a hash-based map instead of line-position alignment.)
- **The React-internal-dispatcher hook shim works for both rectangle-node and geometric-node renderers.** The pattern from icon-node.test.tsx (intercept React's `__SECRET_INTERNALS_DO_NOT_USE_OR_YOU_WILL_BE_FIRED.ReactCurrentDispatcher.current`, return synchronous useState values + no-op setters) directly portable to other node renderers — copy the renderWithHooks + isElement + findAll helpers into a new `.test.tsx` and you can render any node component without a real React Flow mount. Component types in the rendered tree are findable either by `===` reference equality (for exported components like StatusBadge) or by `.name` (for local functions inside the renderer file like PlayButton). The memo descriptor (`{ type: InnerImpl }`) wraps the inner component; index into `.type` to find local-component children.
- **`findByComponentName` is the right tool for asserting on local (non-exported) renderer components.** PlayButton is a function defined inside rectangle-node.tsx. Without exporting it, the test can't `===` compare against the reference. The shim leaves it as `{ type: <function>, props: {...} }` in the tree, and the function's `.name` property survives bundling — so `el.type.name === 'PlayButton'` is a reliable predicate. Same idea works for any memo'd local: walk the memo descriptor's `.type.name`.
- **NodePatchBodySchema doesn't expose every per-type field as a body key.** Image-only `path`, html-only `html`, etc. don't have top-level entries in NodePatchBodySchema — there is no REST route surface that accepts `path` directly. The per-type field-policing happens at TWO levels: (1) NodePatchBodySchema.strict() rejects unknown top-level keys at the route boundary; (2) FlowSchema's per-variant `.strict()` rejects extra keys at the on-disk persist boundary. The operations.test.ts coverage for "cross-type fields rejected" therefore tests the disk-level fence (the load-bearing one) by constructing the malformed node directly + asserting `FlowSchema.safeParse(...)` fails — bypassing the route altogether. This mirrors the architecture's "strict-on-disk, lenient-through-the-route" invariant.
- **Capabilities are schema-accepted on every type; chrome is rectangle-only at the renderer.** The two layers are decoupled: schema says "playAction is valid on a database"; renderer says "GeometricNode draws no play button". The renderer tests (geometric-node.test.tsx) fence the second half — even when `data.playAction` AND `data.statusReport` are both set on a database, no chrome appears. This is the load-bearing invariant of the Renderer phasing rule from the design doc; the per-tag table in geometric-node.test.tsx will trip if a future PR tries to "add a status pill to databases" without thinking through the rectangle-only constraint.
- **`registerFlow` helper in studio-fixture.ts is the right shape for adding e2e flows on a shared worker.** Per-test flow registration (vs. one flow per worker) keeps the kitchen-sink fixture stable while letting new tests seed arbitrary shapes. The pattern: studio.home is the worker-scoped repo root → `mkdirSync(join(home, slug))` → splitFlow + writeFileSync → POST /api/flows/register. Use it for any new e2e test that needs a different node set than kitchen-sink.

**Learnings for future iterations**

- **The studio's prod SPA is `apps/studio/dist/web/`, a static bundle from `apps/web` build. Anytime canvas source changes during a refactor, run `bun run --filter @seeflow/web build` to refresh it.** `vite.config.ts` aliases `@seeflow/canvas` → `packages/canvas/src/index.ts` in both dev and build modes, so canvas source IS what apps/web's build reads. The orchestrator (`apps/studio/scripts/test-integration.ts`) has a mtime-based freshness check that auto-rebuilds, but `apps/studio/scripts/run-e2e.ts` does NOT — so a direct `bun run test:it:update-snapshots` run can use a stale prod SPA if you didn't rebuild manually. The e2e failures with "0 elements found" for `[data-node-type='rectangle']` are the classic symptom — the SPA still has the OLD type-tag routing and renders blank fallback nodes.
- **Strict on-disk schema rejects unknown keys; the studio's API surfaces this as a vague 'badSchema' route error.** When the SPA shows 'Couldn't save change: Flow failed schema validation' but no specific field complaint, look at: (a) `merge.ts`'s NODE_DATA_FLOW_KEYS / NODE_STYLE_KEYS routing — any key not in either set lands in flow.json's data block — and (b) the strict schema in `apps/studio/src/schema.ts` for that variant. US-005's progress doubled down ("kept as-is since the canvas package's typecheck accepts it via the index signature on ShapeDataDefaults and NodeCreateInput.data: Record<string, unknown>"). But while the path through the canvas adapter was permissive, the path through the studio's strict FlowSchema rejected the unknown key — and US-009's e2e draw-mode test exercised that path end-to-end for the first time, surfacing the bug. **Lesson: when a US notes "X is tolerated for now", schedule a follow-up to clean it up rather than letting it accumulate.** Multiple later stories silently relied on the tolerance.
- **Ellipse's renderer reads `data.description`, not `data.name`, for its primary label** — and the same is true for sticky. Under the flat schema, both variants display description-only by default (renderSingleLabelAsDescription). The detail-panel and detail-panel.test.tsx already encode this distinction in `isDescriptionLabelShapeNode`, but the fixtures still tend to set `data.name` because that's the default mental model. Any fixture seeding an ellipse/sticky that's supposed to render visible text MUST set `data.description`.
- **For draw-mode shape buttons under the flat schema:** only `rectangle` + `ellipse` are top-level toolbar buttons (TOP_PRIMARY_SHAPES). `sticky` + `text` are in their own SECONDARY_PRIMARY_SHAPES cluster (different testid: `toolbar-shape-sticky` / `toolbar-shape-text`, still top-level). Any e2e or test that wants to arm an illustrative shape must click the picker first.

Use this for any test that needs to fire a pointer event on a specific DOM element regardless of what's stacked above it (popover backdrops, draw ghost overlays, etc.). The standard `page.mouse.*` API targets coordinates, which intermittently hits the wrong element.
- **The orchestrator runs integration tests BEFORE e2e** (sequential), so flakes in the integration tier block the e2e tier from running. If an integration test is flaky on first invocation but reliable on retry, the orchestrator will give up at step 1 — you won't see the e2e tier's status at all. Re-running `bun run test:it:bun` in isolation will pass while `bun run test:it` (full orchestrator) fails on the same code.

Check `grep -c "playNode" apps/studio/dist/web/assets/index-*.js` — if any quoted occurrences of the OLD tags survive, the SPA is stale. The build alias in vite.config.ts means a fresh apps/web build picks up canvas source changes WITHOUT a separate canvas dist rebuild.

Snapshot regeneration is the slowest gate in the loop — defer it until typecheck/lint/unit tests are green AND you've verified the prod SPA bundle is fresh.
