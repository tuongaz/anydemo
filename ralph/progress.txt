# Ralph Progress Log — component-node-implementation (main)

## Codebase Patterns
- Bun workspaces: root `package.json` lists `apps/*` + `packages/*`. Cross-workspace deps use `"workspace:*"` (apps/studio → @seeflow/canvas) or `"file:../../packages/canvas"` (apps/web — already pinned that way). Both resolve as symlinks under the consuming app's `node_modules/`.
- Use `bun pm view <pkg> versions` (NOT `npm view`) before pinning third-party deps — PRDs may suggest version ranges that pre-date the actual package history.
- After modifying `package.json`, run `bun install` then `bun run typecheck` from repo root. `bun run typecheck` uses `--filter '*'` to typecheck every workspace.
- `bun run format` (biome write) then `bun run lint` (biome check) before commit, per CLAUDE.md.
- Biome's `organizeImports` enforces ALPHABETICAL named-import order — `{ COMPONENT_NAMES, componentCatalog }` (uppercase first), not insertion order. `bun run format` does NOT auto-fix this; only `bun run lint` flags it. Run lint before committing — format alone leaves named-import sort errors in place.
- The repo `bun test` output shows a `[registry] failed to load …` warning from `apps/studio/src/registry.test.ts` — this is an intentional malformed-JSON case, NOT a regression.
- @seeflow/canvas builds via `tsup` with multi-entry config (`{ index, catalog }`). Adding a new public-API subpath = (1) add entry to `tsup.config.ts`, (2) add the matching `"./<sub>"` block to `package.json` `exports`, (3) run `cd packages/canvas && bun run build:js`. `dist/` is in `.gitignore` — GHA commits it on `main` for external npm consumers; local dev resolves via the workspace symlink.
- `Record<K, V>` index access in canvas tests is treated as possibly-undefined under `noUncheckedIndexedAccess`. Pattern: pull the entry into a local, then `if (!entry) throw new Error('unreachable')` before chaining off it. Don't try `expect(entry).toBeDefined()` as a type guard — Bun's `expect` does not narrow.
- Adding a new `NodeType` enum member is a multi-file change: `Record<NodeType, …>` maps in `apps/studio/src/layout.ts` (`DEFAULT_DIMENSIONS`) and `apps/studio/src/operations.ts` (`SEMANTIC_KEYS_BY_TYPE`) MUST gain the new key or `bun run typecheck` fails. Grep for `Record<NodeType` / `Record<z.infer<typeof NodeTypeSchema>` before declaring schema-only changes "done". The matrix tests at the bottom of `schema.test.ts` use a hard-coded `ALL_TYPES` array (NOT the enum), so they don't need updates when adding a new type — though future stories may want to extend them.
- `ResolvedFlowSchema.superRefine` (apps/studio/src/schema.ts) is the cross-field validation seam — every per-node invariant that depends on inter-field state (image-path prefix, component catalog match, future spec/action cross-refs) lives there. Add new checks as a separate `resolved.nodes.forEach((node, idx) => …)` block inside the existing superRefine; keep error `path:` rooted at `['nodes', idx, 'data', …]` so the watcher's joined-issue-paths error message highlights the offending node.
- `readMergedFlow` (apps/studio/src/watcher.ts) is the disk -> ResolvedFlow pipeline: (1) parse flow.json via `FlowSchema` (on-disk shape), (2) merge with style.json via `mergeFlowAndStyle`, (3) inline component spec sidecars via `inlineComponentSpecs`, (4) re-validate the inlined shape via `ResolvedFlowSchema.safeParse` so superRefine cross-field checks run. Any new on-disk-only validation belongs in `FlowSchema`; any check that needs inlined spec/style state belongs in `ResolvedFlowSchema.superRefine`. The double-parse is intentional — don't try to fold them together.
- Externalized JSON sidecars (e.g. component `spec` -> `nodes/<id>/spec.json`) are a different pattern from externalized text fields (`detail` -> `detail.md`, `html` -> `view.html`). Text fields use `EXTERNALIZED_NODE_FIELDS` + the `file://<name>` ref on `data.field`; JSON sidecars keep the OBJECT inline on the in-memory ResolvedFlow (for the post-mutation parse + SSE broadcast) and rely on `splitFlow` to STRIP the key per-type before writing flow.json. The resolver (e.g. `inlineComponentSpecs`) re-attaches the object on read. Don't add JSON sidecars to `EXTERNALIZED_NODE_FIELDS` — that pipeline is hardcoded for string content + file:// refs.
- `mutateMergedFlow` (apps/studio/src/operations.ts) does NOT inline component specs before handing the merged flow to the mutator. The mutator sees `FlowSchema`'s on-disk shape (no `data.spec` for component nodes). This means a PATCH on a component node that doesn't carry `spec` will trip the post-mutation `ResolvedFlowSchema.safeParse` (which requires `data.spec` on type==='component'). For now, every component PATCH MUST include the full `spec` field. If a future story needs spec-preserving PATCHes (e.g. just renaming a component node), inline specs inside `mutateMergedFlow` between `mergeFlowAndStyle` and the mutator — parallel to what `readMergedFlow` does today. Don't try to make `spec` optional on `ResolvedComponentNodeData` — that breaks the validation contract.
- Script-spawn runners (proxy.ts:runPlay, proxy.ts:runReset, component-action-runner.ts:runComponentAction) share the same shape: realpath-guarded `resolveScript`, concurrent stdout/stderr drain (so OS pipe buffers don't deadlock the child), JSON-encoded payload to stdin written BEFORE awaiting exit, and SIGTERM → 2s grace → SIGKILL escalation on timeout via a `killWithGrace` helper. New runners should mirror this pattern verbatim rather than re-inventing it — the deadlock + escape edge cases are subtle. The differences between runners are: (a) which env vars they set (SEEFLOW_DEMO_ID/NODE_ID/RUN_ID universally; component-action adds SEEFLOW_ACTION_NAME), (b) the default timeoutMs (proxy = 30s, component-action = 5s), (c) whether they broadcast SSE events (proxy does; component-action does NOT — the API caller maps statusHint to HTTP and the canvas runtime is the only consumer). Use `statusHint` (not events) as the channel for HTTP runners.
- Local in-memory ProcessSpawner fakes (`makeFakeSpawner` in proxy.test.ts AND component-action-runner.test.ts) are intentionally duplicated per test file rather than extracted into a shared helper — each runner has slightly different needs (proxy needs `killExitsOn` to model "SIGTERM-ignoring" children for grace-then-SIGKILL paths; component-action's tests don't yet need that level of control). If a third runner shows up, consider lifting the fake into `test-helpers/process-spawner-fake.ts`. Until then, the small per-file duplication is preferable to a premature abstraction that would have to grow new knobs for every new caller.
- HTTP routes that spawn processes (`/play`, `/reset`, `/actions/:name`) all share the same boilerplate: registry lookup → events bus guard → `resolveFilePath` → `existsSync` → `readMergedFlow` → node lookup → type/capability gate → runner call → HTTP status mapping. Take `processSpawner` (and `proxy` / `statusRunner` when relevant) from `ApiOptions` and pass it through to the runner so tests can inject an in-memory fake via `createApp({ processSpawner })`. Status mapping: the runner returns `statusHint` and the route casts it to the literal union of valid HTTP statuses (`400 | 404 | 500 | 504` for component actions; the play route uses a different shape) — don't try to use Hono's `StatusCode` import for this, the cast is the pragmatic seam. New process-spawning routes should mirror this shape verbatim — see `api.ts:/flows/:id/nodes/:nodeId/actions/:name` for the canonical form.
- Biome's formatter has a soft line-length preference: a 100+ char line that lints clean (no `useTemplate` violation) often re-wraps after a string-concatenation → template-literal change, which then trips the format rule. Don't try to manually wrap to fix `useTemplate` — apply the template-literal change first, then run `bun run format` and let Biome decide whether to keep the line single or wrap it. Trying to wrap proactively can land you in a flip-flop where format unwraps your manual wrap and lint complains again.
- Adding a new `NodeType` tag to `packages/canvas/src/types.ts` cascades cleanly through `NodeKind = NodeType` in `adapter/types.ts` — no adapter changes needed. The canvas-side `nodeTypes` map in `seeflow-canvas.tsx` is NOT a `Record<NodeType, …>` (just an object literal), so it won't compile-error on a missing arm; remember to wire the renderer when its dedicated story lands. There are NO `Record<NodeType, …>` or exhaustive switches on NodeType in `packages/canvas/src/` today (verified by grep) — the studio-side `Record<NodeType, …>` maps (DEFAULT_DIMENSIONS, SEMANTIC_KEYS_BY_TYPE) are the only compile-time exhaustiveness pin, and they're already covered by the studio CLAUDE.md / Codebase Patterns guidance. To future-proof, types.test.ts now carries an explicit exhaustive switch with a `never`-typed default arm — touching NodeType will compile-error in that test until the new variant gets an arm.
- The canvas package's test file conventions: tests live BESIDE their source files (`foo.ts` + `foo.test.ts`). The new `types.test.ts` is the first top-level `src/*.test.ts` — convention extends fine. Use `import { describe, expect, test } from 'bun:test'` (matching the rest of the workspace).
- The html-node test harness (React's `ReactCurrentDispatcher.current` swap) ships with a NO-OP setter for `useState` — which is enough for HtmlNode (it reacts to props, not internal state) but BREAKS for any component whose tests need to observe a state mutation. Pattern used in `component-runtime.test.tsx`: keep the dispatcher-swap, add module-level `slots` + `cursor` that PERSIST across renders within a test, clear in beforeEach/afterEach, and reset `cursor = 0` per render (a slot per useReducer/useState call site). useCallback / useMemo / useRef / useEffect can stay as pass-throughs / no-ops; the seam is just useReducer + useState. When the next stateful node needs the same harness, lift this into `test-helpers/hook-shim.ts` — until then, copy verbatim. The dispatcher-internals path is `(React as any).__SECRET_INTERNALS_DO_NOT_USE_OR_YOU_WILL_BE_FIRED.ReactCurrentDispatcher.current` (React 18; will change in React 19+).
- Biome's `useShorthandFunctionType` lint (only triggered by `bun run lint`, not by `bun run format`) flags object-literal types containing only a call signature: `const fn = X as unknown as { (a: A): R }` must be `const fn = X as unknown as (a: A) => R`. Apply the fix when prompted — it's a Safe fix, the lint output is exact, and the underlying types are semantically identical.
- Discriminated-union slot storage (`Slot = ReducerSlot | StateSlot`) does NOT narrow through `let slot = slots[i]; if (!slot) { slot = {...}; slots[i] = slot; }` because TS sees the outer `let slot: Slot | undefined` and never refines to one arm. The fix: capture `const existing = slots[i]`, then `if (existing && existing.kind === '<kind>') slot = existing; else { slot = { kind: '<kind>', ... }; slots[i] = slot; }` with `slot: ReducerSlot` (or StateSlot) typed explicitly. Now `slot.state` (or `slot.value`) compiles. Don't try `as ReducerSlot` casts on the union access — the linter will complain about the unsafe assertion and it's harder to read.
