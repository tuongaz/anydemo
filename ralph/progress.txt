## Codebase Patterns
- `apps/studio/src/share-*.ts` is the existing flat convention for live-share modules. Phase-7 SSE work introduces a `src/share/` subdirectory for new files — both styles coexist.
- StudioEvent + EventBus live at `apps/studio/src/events.ts`. Bridged SSE event types are the 5 starting with `flow:` or `node:` (NOT `file:changed` / `registry:reload`, which stay host-local).
- Envelope wire shape is centralized in `apps/studio/src/share-envelope.ts` (host) and `seeflow-viewer/src/lib/share-envelope.ts` (peer). Adding a new envelope `type` requires updating BOTH.
- Cross-repo schema parity is enforced with SYNC-WITH-PEER markers + a `scripts/check-*-sync.ts` script that normalizes whitespace+comments. The peer mirror lives in the sibling repo at `/Users/tuongaz/dev/seeflow-viewer/`; sync scripts must walk parent dirs to locate it and soft-pass when absent.
- Per-peer addressed broadcast pattern: peer-targeted frames use `broadcast(makeEnvelope(type, payload, { to: peerConnId }))` where peerConnId is `env.from` captured during presence/join (NOT the peerId — the relay routes on conn id). `to: 'all'` is reserved for fan-outs.
- Per-frame size cap pattern: when a wire frame must fit a byte cap, write a generic `chunk<T>(...): T[][]` over the natural partitioning unit (here per-flow), measure with `JSON.stringify({ wrapperShape }).length`, and stamp `{ chunk: 0..N-1, total: N }` only when N>1. Single-chunk frames omit the headers so the common path stays small.
- Bun directory test discovery skips `*.it.ts`. Use `bun test src/...` for unit + share tests; `bun run test:it:bun` for integration.
- `bun run format` must run BEFORE `bun run lint` (Biome).
- `apps/studio/src/watcher.test.ts` has pre-existing flaky fs-watching failures unrelated to share work — ignore in CI gating unless you touched watcher code.
- TypeScript narrows `let x: T | null = null` to `null` for the surrounding scope even when later writes happen inside injected callbacks. When testing schedule/cancel injection, capture the value via an object box (`const ref: { value: T | null } = { value: null }`) instead of a bare `let`.
- Canvas package consumes a built `dist/` (tsup): after editing public types under `packages/canvas/src/`, run `bun run --filter @seeflow/canvas build` before the seeflow-viewer can import the new symbol — the viewer's `@seeflow/canvas` resolves to `dist/index.d.ts` even though node_modules is symlinked.
- Canvas public API extension pattern: declare new types in their owning module (e.g. `adapter/io-adapter.ts`), then add them to the matching numbered section of `packages/canvas/src/index.ts`. Forgetting the barrel export silently keeps the type internal to the package.

Don't add `'sse'` to `TYPED_FRAME_EVENTS` — those buckets are keyed by `envelope.type`, but the dispatch happens via the generic frame channel inside `dispatchSseFrame` (which is also the public API for tests that need to inject frames synchronously without crossing the WebSocket).
  - `StudioEvent` (the viewer-side type) deliberately omits `seq` — `seq` is internal sequencing metadata, and exposing it through the sink would let canvas consumers branch on host-internal counters. Keep it `{ type, flowId, ts, payload }` to match the host's existing StudioEvent contract.
  - Terminal-wins seq override: even when a stale `node:done`/`node:error` arrives, it MUST settle the visual state. Otherwise a reordered terminal could leave the canvas stuck in a running state forever. The implementation does NOT bump `lastSseSeq` for the stale terminal — it just emits — so a later non-terminal with a higher seq would still re-take ownership of seq tracking (very rare in practice but the semantics are precise).
  - Reconnect detection lives in the state listener. There's no "previously connected" check — on every `closed`/`kicked`, the gate flips on. First connect (`idle` → `connecting` → `authed`) never trips the listener, so the gate stays off until the first disconnect. Live events are processed normally during the initial session — the snapshot just primes badges to match the host's current per-node status.
  - `extractNodeIdFromSsePayload(data)` is a module-level helper (not a class method) because it's pure and reusable. If a future story needs to extract more SSE payload fields (e.g. `progress` for node:status visualization), keep them as separate module-level helpers rather than methods.

- Learnings for future iterations:
  - The drain loop runs `void drain()` after every enqueue, but drain is idempotent (`if (draining) return`) so the active loop just keeps draining the new tail. Crucially, the FIRST enqueue starts drain synchronously and drain SHIFTS the first frame BEFORE awaiting `opts.send` — so by the time the caller's next statement runs, the head of the queue is already "in-flight" (not counted in `queueDepth`). Test expectations must account for this: with maxFrames=4 and 10 burst enqueues, `queueDepth=4`, `droppedFrames=5` (10 - 1 in-flight - 4 in queue = 5 dropped), NOT 6.
  - The legacy `to: 'all'` SSE broadcast remains the fan-out path when `peerSseQueues.size === 0`. This keeps the existing US-067 share.sse-bridge tests passing without modification — those tests broadcast SSE events with no peers registered. The trade-off is a small dual-path branch in the tap's `onEvent`. Don't remove it without first migrating all such tests to register a peer via presence/join first.
  - The US-068 SSE tap rate limiter (60/sec burst 120 default) is UPSTREAM of the per-peer queues. Bursts > 120 within the bucket window are absorbed by the tap before reaching the queue. For backpressure tests that need to flood the queue, pass `sseTapRateLimit: false` to disable the tap-level coalescer. Production traffic still benefits from BOTH layers — the tap protects against `node:status` storms across all peers, the queue protects each peer's specific consumer speed.
  - `lastSendMs` is the DURATION of the last awaited send in ms (not a timestamp). The "slow peer" warning in the UI can flag this rising above some threshold (e.g. ~250ms+) as a signal of network saturation on the peer end. Don't confuse with "ts since last send" naming patterns elsewhere.
  - On rolling-window drop pruning: each drop pushes `now()` into `dropTimestamps`; pruning shifts entries older than `now - dropWindowMs`. The threshold check is strict-greater-than (`> dropThreshold`), so threshold=5 fires on the 6th drop within the window. After firing, the array is cleared so the next firing requires another full window of drops — prevents thrash.
  - `enrichWithSseMetrics` is invoked on EVERY state() call AND every subscriber dispatch in setState — that's intentional. Metrics are live (queueDepth/droppedFrames update on every enqueue), so a subscriber reading via /api/share/state's initial subscribe callback gets a fresh snapshot, not a stale one frozen at the last transition.
  - When testing FIFO drop policy, the very first frame (step 0) often appears in the sent list because drain locked it in-flight before any drops occurred. Assert on the ABSENCE of early-queued frames (e.g. step 100, step 200) NOT the presence of "first sent step > 0". The in-flight slot is outside the eviction policy's reach.
  - `Map<connId, PeerSseQueue>` is keyed by connId (not peerId) to stay in lockstep with `connPeers` — the relay routes on connId. `peerConnIds` (peerId -> connId) is the inverse for kick() / metric enrichment paths that start from peerId.
